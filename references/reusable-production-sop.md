## 1. 适用范围与继承边界

直接复用到新的历史题材、人物传记、历史知识系列：一张图承担一个信息动作，连续旁白，静态切镜。迁移到科普、商业、文化解说时，可复用拆稿、对齐、资产追踪、QA 方法；必须重新建立领域事实核查与视觉合同，现有历史提示词不能直接批量套用。动画、真人拍摄、口型同步不属于本 Skill 的已验证生产模式。

先读目标目录自己的 `AGENTS.md` 和用户当轮要求，再读 `project.json`。项目合同覆盖 Skill 默认值；不要将其他目录的项目合同复制为新项目的规定。

| 可复用 | 新项目必须重新建立 |
|---|---|
| 阶段顺序、目录、ID、alignment、QA、返工方法 | 主题、受众、平台、成功标准、来源与脚本 |
| 四种风格的描述和压力测试方法 | 本项目的单一风格选择、参考图使用范围 |
| 人物卡和母版机制 | 人物身份、时代、外貌设计和场景 |
| 工具脚本、Remotion 模板、成本记录格式 | voice ID、模型、预算、批次与调用授权 |
| 候选隔离和哈希验收 | 听审、审图、候选批准与发布证据 |

不要继承旧项目的 `approvals`、`workflow.history`、任务 ID、QA pass、人物图片、旧路径或旧字幕时间。参考图只在明确用途后登记；模型、价格与提供商限制在下一次实际调用前核实，不把某集一次成功写成永久保证。

## 2. 新项目启动

用户可以这样发起：

> 用 $make-static-history-video 开一个新的历史解说项目。主题是【主题】，面向【受众】，发布到【平台】，素材在【路径或链接】。先完成 brief、资料和脚本核查、生产合同、分镜及费用预览，未批准前不付费生成。

先从用户材料填写 `brief.md`；未知内容标为待定，只有改变目标、成本或验收标准时才询问。名字、目录命名等可逆选择说明假设后继续。脚本已定稿时直接从核查恢复，不强迫补做对标或写作包。

将 `SKILL_ROOT` 设为本 Skill 所在的绝对目录；不要假定当前工作目录就是 Skill。

```bash
SKILL_ROOT="${CODEX_HOME:-$HOME/.codex}/skills/make-static-history-video"
python3 "$SKILL_ROOT/scripts/init_project.py" /absolute/new-project --title "新项目" --guided
python3 "$SKILL_ROOT/scripts/manage_workflow.py" summary /absolute/new-project
python3 "$SKILL_ROOT/scripts/manage_workflow.py" validate /absolute/new-project
```

初始化拒绝非空目录；自动创建 `brief.md` 和 `feedback/production-review.md` 空模板。`--guided` 未显式指定音色或模型时不读取另一个项目遗留的音色、模型环境默认值。默认生产参数只是起点，`settings_confirmed=false`，全部付费与验收状态保持未批准。源脚本原样存到 `source/original-script.md`；修订稿另存 `source/execution-script.md`，在 `project.json.source` 登记当前执行稿与哈希。

## 3. 阶段交付与验收

| 步骤 | 操作与产物 | 进入下一步的条件 |
|---|---|---|
| 1 内容 | brief → 来源 → 必要时对标与写作包 → 定稿 → `source/fact-check.md` | 事实、判断、未知已分开，阻断错误为零，执行稿确定 |
| 2 合同 | `project.json` 固定画幅、风格、音色模型、字幕、BGM、批次、预算及验收范围 | 必须的选择和付费范围已有用户依据 |
| 3 分镜 | shot 管口播语义段，frame 管实际图片；绑定台词与词锚，识别 strict 角色 | 一个 frame 一个核心动作，角色与文字清单完整 |
| 4 配音 | 连续配音 → 完整性检查 → 必要且已获批准的缺段补配 → 最终音频与 alignment | 文本和时间覆盖完整；全片 1× 与每个接缝前后至少 3 秒听审通过 |
| 5 视觉 | 选择风格 → strict 角色脸部及全身母版确认 → 提示词预检 → 钩子、人物、地图、文字压力帧 | 母版先于含该角色的压力帧；不适用类型写明原因；样图问题解决 |
| 6 批量图片 | 独立单图四并发，保存原图、canonical PNG、任务和哈希 | 逐张原尺寸审查，P0/P1 为零；错图仅定向修复 |
| 7 对齐 | 从最终配音重建 SRT、caption manifest、timeline | 时间连续，旁白重叠为零，SRT Unicode 标点为零 |
| 8 候选 | Remotion 静态合成 + BGM + 最终 H.264 编码 | 固定帧率、切点关键帧、音频规格满足合同；先存 candidates |
| 9 QA | 全解码、每个切点、响度、黑帧静音、图像与配音人工检查 | 技术、内容、听审三项分别通过并绑定当前文件 SHA256 |
| 10 交付 | 展示具体候选、缺项及报告；用户接受该版本后晋级 | 正式文件与批准候选哈希一致；平台发布另有证据 |

单轮已获授权的工作连续推进，不把表中每一步都变成重复提问。`workflow` 是进度记录；不能用手填“已通过”替代产物和 QA。状态使用 `manage_workflow.py` 支持的六种值，具体通过理由写入 history 或报告，避免旧项目的自造状态使恢复失效。

配音特别检查：HTTP 成功、能播放、字符数组覆盖全文均不证明说完全文。核对请求文本、三个 alignment 数组等长、时间单调且不越过实测音频、尾部可发音字符没有被钳成零时长。使用 `scripts/check_voice_alignment.py`；检测失败是定位线索，不据此自动剪音或扣费重配。完整听审仍必需。

详细命令分别读取主 Skill 的配音、提示词、人物和发布 QA 参考。`npm run render` 只产生基础候选，不保证切点关键帧或响度；按 `release-qa.md` 完成编码与检查后才能交付为已通过 QA 的候选。

## 4. 费用与失败恢复

付费前把下列信息作为具体预览放入 `logs/generation-plan.json`，批准依据登记到 `project.json.workflow.history`，不凭模板生成授权：

- 本轮对象 ID、数量、提供商、模型、文本或提示词哈希。
- 母版、压力帧、批量场景、配音和预留返工分别多少；禁止重复计数。
- 估算单价、币种、查询日期、预算上限、批准覆盖哪些失败重试。
- 估算与实际账单分开；没有实际扣费证据时写“未知”，不把 0 代替未知。

台账按每次请求记录 `task_id/request_id`、对象 ID、输入哈希、提交时间、状态、结果文件和哈希、耗时、估算、实际费用与证据。环境变量只检查是否存在，不打印值，不把密钥写进台账或备份。

失败恢复：

1. 返回状态未知，先按原 task/request ID 查询或读取服务历史，避免重复提交和扣费。
2. 找到同输入哈希且审查通过的资产，验证文件和哈希后复用；不以同名文件或存在缓存作为充分证据。
3. 请求超时或音频内容不完整时，定位最早缺失的完整 shot。只对批准范围内的缺段恢复；保留原响应和可用前缀。不要把某次约九分钟截断推断成服务固定时长上限。
4. 同因连续失败两次且没有新证据，停止同样重试；整理失败对象、证据、已花费用及最小下一步，继续无依赖工作。
5. P0/P1 修复是必要工作；单纯审美偏好不自动触发付费重做。新增次数、成本或付费路径超出原批准时，先准备具体修复预览。

## 5. 返工影响表

| 改动 | 必须重新验证的链路 | 可以保留 |
|---|---|---|
| 修正某张图 | 当前原图审查 → PNG/JPEG 哈希 → public/缓存 → 候选 → 受影响实帧和全部切点 | 未改的配音、SRT、时轴数值 |
| 改一句台词或发音 | 受影响配音 → 合并音频 → 完整性与听审 → alignment → SRT → timeline → 候选与 QA | 语义仍一致且重新核定的图 |
| 更换模型或音色 | 从完整带标点脚本生成新音频，重建整个对齐链路并听审 | 确认仍匹配新台词的图；不得套旧 SRT |
| 增减停顿或后期变速 | 保存编辑映射，更新所有后续字符、接缝、字幕、镜头时间，重新听审与渲染 | 未改的画面资产 |
| 修改 BGM 或整体响度 | 混音 → 候选 → 实测 LUFS/真峰值、解码、声画时长 | 文本和未改的图 |
| 修复封装/切点 PTS | 最终编码 → 全片 PTS 和每切点归属、关键帧 → QA 新哈希 | 已审资产和配音内容 |

候选、听审报告、timeline 和实际用于合成的音频必须属于同一版本。任何重新编码都会产生新视频哈希，旧 QA 不能直接沿用。更换正式版时保留旧版与 `superseded` 指向，在交付记录里明确当前生效文件；不要只看某个 `release.json.passed=true`。

脚本指定的黑场、停顿与终卡应逐项登记帧区间、原因和批准依据；仅豁免这些精确区间。禁止为了通过 QA 把异常全体标成“有意”。

## 6. 性能选择

默认继续使用 canonical RGB PNG。图片较多时可以在新项目合同中显式选择 JPEG 工作图，先对人脸、细字、墨线等代表图做原尺寸对比：

```json
{"render_image_format":"jpeg","render_jpeg_quality":92,"render_jpeg_subsampling":"4:4:4"}
```

```bash
python3 "$SKILL_ROOT/scripts/sync_remotion_assets.py" /absolute/project
python3 "$SKILL_ROOT/scripts/prepare_compressed_images.py" /absolute/project
```

后一个命令保留原图和 PNG，仅创建同尺寸 JPEG，更新 timeline 中图片路径并写哈希报告。首次修改前备份 timeline；再次运行复用已验证结果；源 PNG 修复后重建对应 JPEG。未知或用户修改过的 JPEG 拒绝覆盖。重建 timeline 或重新同步之后再次运行。PNG 默认路径没有变化。

压缩减少工作图体积，不等于已释放磁盘。不要删除原图、旧候选或缓存来证明“优化成功”。

长静态无字幕视频可考虑“Remotion 每个不同画面渲染一次，再按精确帧数保持”的方法；本 Skill 默认入口仍是标准 Remotion 渲染。项目专用的分段编码器不能直接当通用 CLI。迁移时先完成含真实切点的本地样片，验证 PTS、视觉归属、音频时长与关键帧；出现字幕、动画、淡变时不能把整个 shot 冻结成一张图。

## 7. 结项与复用

填写 `feedback/production-review.md`：交付范围、当前成片与哈希、来源和执行稿、工具版本、已通过与未执行检查、费用证据、人工介入、失败及修复、待验证事项。

结项不是新的发布或清理授权，也不补写从未执行的人工验收。不能从“项目做完”推断市场需求、流量或收益已验证。

下个项目只带走更新后的 Skill、空模板和确有适用范围的参考；不复制整个 build、旧审批或 `.env`。修改生产 Skill 前保存可恢复备份；更新后至少执行结构校验、独立项目初始化、必要脚本用例和无付费的真实材料检查。验证记录留在结项项目，不把一次项目的成本、任务 ID 和地方路径写成通用默认值。
